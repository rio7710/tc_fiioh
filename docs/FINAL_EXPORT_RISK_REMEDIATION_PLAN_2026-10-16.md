# Final export risk and remediation plan

- 작성일: 2026-10-16 (Asia/Seoul)
- 상태: 검토 완료, 구현 전
- 범위: STEP 04 최종영상 요청부터 FFmpeg 합성, 산출물 등록, STEP 05 캘린더 반영까지
- 작성 방식: 주 에이전트와 tmux `tcmini:2`의 독립 코드 검토 결과 통합
- 독립 검토 원문: `docs/FINAL_EXPORT_REMEDIATION_DESIGN_REVIEW_2026-10-16.md`
- 변경 원칙: 잘못된 결과의 성공 처리를 먼저 차단하고, 이후 복구성과 운영 효율을 개선한다.

## 1. 확인된 현재 상태

- 마지막 실제 최종영상 작업 `render-1792065162676-l6y819`은 성공했다.
- 17개 장면, 62.44초, 16:9·9:16·4:5 출력이 등록됐다.
- SQLite `integrity_check`와 외래키 점검은 정상이다.
- 데이터 볼륨 사용률은 점검 당시 33%였다.
- 최근 화면 오류 시 `/render` 요청과 실패 큐 레코드는 없었다. 세션 복원 전에 `/api/render-settings`가 401을 반환한 기록이 있었다.
- 최종영상 워커는 한 개이며 메모리 제한은 1536MB이다.
- 현재 문서는 위험 분석과 구현 계획만 저장한다. 코드, DB, 컨테이너, 배포 상태는 변경하지 않는다.

## 2. 반드시 지킬 계약

1. 최종영상 입력은 큐 등록 시점의 불변 스냅샷이어야 한다.
2. 운영 렌더에서 데모 영상이나 데모 음성을 대체재로 사용하지 않는다.
3. 한 장면은 확정된 `media_type`과 선택된 산출물 하나만 사용한다.
4. 음성·자막·장면 시간은 동일한 cue/timeline 계약을 사용한다.
5. 같은 논리 입력은 한 작업으로 멱등 처리한다.
6. 모든 출력 비율의 산출물과 캘린더 반영은 하나의 최종 확정 단위다.
7. 실패 원인은 진단 가능하게 보존하되 브라우저에는 비밀값, 로컬 경로, 스택을 노출하지 않는다.
8. 작업 상태는 `queued`, `running`, `succeeded`, `failed`, `cancelled` 중 하나로 명확해야 한다.

## 3. 위험 목록

### P0 — 오류 없이 잘못된 결과가 성공할 수 있는 위험

#### R-01. 리비전과 설정이 큐에 고정되지 않음

- 큐에는 `project_id`와 요청 payload가 저장되지만 확정 `revision_id`가 필수 입력이 아니다.
- 워커는 실행할 때 최신 STEP 03 리비전, 사용자 렌더 설정, 브랜드 선택을 다시 조회한다.
- 대기 중 대본, 음성 프로필, 이미지 선택, 브랜드 설정을 바꾸면 사전검증한 입력과 실제 렌더 입력이 달라질 수 있다.
- 임대 만료 재시도에서도 같은 작업이 다른 입력을 사용할 수 있다.

#### R-02. 장면 미디어 누락 시 데모 영상이 들어갈 수 있음

- 선택 영상과 이미지가 모두 없을 때 `scene_video_path`가 병합 데모 영상을 반환할 수 있다.
- 결과는 실패가 아니라 정상 MP4로 생성될 수 있다.

#### R-03. 음성 누락 시 데모 나레이션이 들어갈 수 있음

- 실행 시점의 `voice_clips`가 비어 있고 장면 수가 데모 트랙 수와 일치하면 데모 음성이 사용될 수 있다.
- 큐 등록 전 음성검증과 워커 실행 시 최신 리비전 재조회가 결합될 때 발생 가능하다.

#### R-04. 재시도 결과에 서로 다른 입력 버전이 섞일 수 있음

- 출력 파일명은 정규화된 `job_id`에 의존한다.
- 기존 출력 재사용은 파일 존재, 크기, 재생시간 중심이며 입력 스냅샷 해시를 확인하지 않는다.
- 앞 비율은 이전 입력의 파일을 재사용하고 뒤 비율은 새 입력으로 생성할 가능성이 있다.

#### R-05. 음성 연결 기준이 cue와 scene 사이에서 일관되지 않음

- 타이밍 계산은 cue 중심이지만 최종 오디오 선택 일부는 `scene_id` 중심이다.
- 같은 장면의 여러 음성 후보, 프로필 변경, 텍스트 변경이 있을 때 오래된 음성이 선택될 수 있다.

### P1 — 실패, 중복, 부분 반영 위험

#### R-06. 전체 자산 사전검증이 없음

- 큐 등록 전에는 음성 준비만 수행한다.
- 선택 이미지, Kling MP4, 워터마크, 비율별 아웃트로, BGM, 자막 입력은 워커 실행 중 확인된다.
- 비싼 자막/앞 비율 합성 후 뒤 단계에서 실패할 수 있다.

#### R-07. 일반 렌더 오류는 설정된 3회 재시도를 사용하지 않음

- 워커는 `RetryableFinalExportError`만 재시도 대상으로 본다.
- 현재 실행기는 일반 FFmpeg·일시적 I/O 오류를 이 유형으로 분류하지 않는다.
- 실제 재시도는 주로 워커 사망과 임대 만료 경로에서만 발생한다.

#### R-08. 원본 오류가 사라지고 사용자 메시지만 일반화됨

- 큐 실패에는 고정된 일반 메시지가 저장된다.
- 운영 로그에도 원본 예외와 단계 정보가 충분히 남지 않는다.
- 반대로 진행률 detail에 원본 FFmpeg 꼬리가 들어가면 내부 경로가 브라우저에 노출될 수 있다.

#### R-09. 비율·브랜드·캘린더 등록이 하나의 트랜잭션이 아님

- 비율별 `register_final_export`, 브랜드 스냅샷, 캘린더 정리가 각각 커밋된다.
- 중간 실패 시 일부 비율만 등록되거나 고아 MP4가 남을 수 있다.
- 프로젝트 삭제와 렌더 등록이 경합하면 작업 상태와 파일 상태가 갈라질 수 있다.

#### R-10. 동일 콘텐츠 중복 작업을 막지 않음

- 버튼 클릭마다 새로운 `job_id`가 만들어진다.
- 동일 사용자·프로젝트·리비전·설정의 진행 중 작업을 재사용하는 제약이 없다.
- 탭 중복, 연결 끊김 뒤 재클릭 시 중복 렌더와 캘린더 버전 증가가 가능하다.

#### R-11. 비동기 작업을 장시간 HTTP 연결로 감쌈

- API와 게이트웨이가 `/render`를 각각 최대 2시간 기다린다.
- 경계 시점에 API의 구조화된 504보다 게이트웨이 502가 먼저 보일 수 있다.
- 브라우저의 연결 실패 복구 확인은 약 10분이라 실제 작업은 계속되는데 화면만 실패할 수 있다.

#### R-12. TTS가 큐 등록 전에 실행됨

- 누락 음성을 생성하는 동안 아직 최종영상 `job_id`가 없다.
- 연결이 끊기면 사용자는 상태를 복구할 수 없고, 중복 요청에서 TTS가 중복 호출될 수 있다.
- 렌더 시작 전 리비전 확정이라는 부수 효과도 발생한다.

#### R-13. 실질적인 취소 기능이 없음

- 큐에는 `cancel()`이 있지만 호출하는 사용자 API와 UI가 없다.
- FFmpeg 실행 루프에 취소 확인과 프로세스 종료가 없다.
- 취소 상태만 바꾸더라도 이미 실행 중인 인코딩은 자원을 계속 소비할 수 있다.

#### R-14. 최종 MP4 서빙에 소유자 검사가 없음

- `/04_exports/<filename>`은 로그인과 프로젝트 소유자 확인 없이 정적 경로로 연결된다.
- URL이 유출되면 비로그인 사용자가 고객 영상을 내려받을 수 있다.

### P2 — 운영 품질과 확장 위험

#### R-15. 단일 FIFO 워커의 전체 사용자 선두 차단

- 한 사용자의 장시간 다중 비율 작업이 뒤의 모든 사용자를 막는다.
- 사용자별 제한과 대기 순번 표시가 없다.

#### R-16. FFmpeg 자체 제한시간과 종료 처리 없음

- FFmpeg가 손상 입력이나 필터 문제로 멈추면 HTTP 제한시간 이후에도 워커를 계속 점유할 수 있다.
- OOM 또는 SIGKILL 후 `.render_work/staged-*` 임시 디렉터리가 남을 수 있다.

#### R-17. 하트비트 예외 처리와 다중 워커 확장 위험

- 하트비트가 SQLite 오류로 종료되면 임대가 갱신되지 않는다.
- 워커를 여러 개로 늘릴 경우 만료된 것으로 판단한 다른 워커가 같은 작업을 실행할 수 있다.

#### R-18. 자막 폰트와 레지스트리의 비결정성

- 자막 생성이 외부 웹폰트에 의존하면 네트워크 상태에 따라 대체 폰트가 사용될 수 있다.
- 파일 레지스트리 잠금은 프로세스 내부 잠금이라 API와 워커가 동시에 쓸 때 안전하지 않다.
- 불완전한 캐시 파일 재사용 가능성도 있다.

#### R-19. SQLite 폴링 부하

- 장시간 `/render` 요청은 0.25초마다 새 연결로 큐를 조회한다.
- FFmpeg 진행률도 같은 SQLite 파일에 자주 기록한다.
- 인증, 자동화, 콘텐츠 API와 잠금 경합이 생길 수 있다.

#### R-20. 출력 파일명 충돌 가능성

- 사용자 입력 `job_id`를 정규화하고 80자로 자른 값을 파일명에 사용한다.
- 서로 다른 원본 ID가 같은 정규화 결과가 되면 기존 MP4를 잘못 재사용할 수 있다.

| --- | --- | --- | --- |
| P0 | 최신 상태 재조회, 데모 영상·음성 대체, 입력 해시 없는 결과 재사용 | 오류 표시 없이 다른 내용의 영상이 정상본으로 확정될 수 있음 | 불변 스냅샷, 데모 대체 제거, 전체 자산 preflight |
| P1 | 긴 HTTP 연결, 중복 작업, 재시도 미분류, 부분 DB 반영 | 502 뒤 백그라운드 중복 실행, 일부 비율만 캘린더 등록 | `202 + job_id`, 멱등키, 오류 분류, 원자적 finalize |

| P1 | 인증 없는 최종 MP4 경로 | URL을 아는 비로그인 사용자가 고객 영상을 접근할 수 있음 | 소유권 확인 다운로드, 필요 시 단기 서명 URL |
| P2 | 단일 FIFO, 잦은 SQLite 쓰기, 외부 폰트·레지스트리 비결정성 | 대기 증가, DB 경합, 렌더 결과 편차 | 사용자별 제한, 쓰기 throttle, 로컬 폰트와 원자 캐시 |

판단 기준은 장애 횟수가 아니라 결과 신뢰성이다. 명시적 실패는 재실행할 수 있지만 잘못된 고객 영상의 성공·캘린더 등록은 발견과 회수가 늦으므로 P0로 처리한다.

## 4. 목표 데이터 계약

큐 입력에는 최소한 다음 불변 필드를 저장한다.

```json
{
  "schema_version": "final-export-job.v2",
  "job_id": "server-generated-uuid",
  "idempotency_key": "sha256:user+project+revision+settings+assets",
  "user_id": "user-id",
  "project_id": "project-id",
  "revision_id": "confirmed-stage3-revision-id",
  "timeline_hash": "sha256",
  "render_settings": {},
  "brand_assets": [],
  "scene_assets": [],
  "voice_assets": [],
  "requested_platforms": [],
  "input_hash": "sha256"
}
```

각 자산에는 논리 ID뿐 아니라 `uri`, `checksum`, `media_type`, 선택 상태, 리비전과 장면 ID를 포함한다. 워커는 최신 상태를 다시 해석하지 않고 스냅샷을 검증해 사용한다.

## 5. 단계별 해결 계획

### Phase 0 — 관측성과 테스트 동결

변경 후보:

- `01_app/final_export_worker.py`
- `01_app/final_export_queue.py`
- `tests/test_final_export_queue.py`
- 신규 최종영상 실패 진단 테스트

작업:

1. 오류에 `error_code`, `stage`, `attempt`, `job_id`, 안전한 메시지를 저장한다.
2. 원본 예외와 traceback은 서버 로그에만 남기고 브라우저에는 내보내지 않는다.
3. 현재 성공 E2E를 고정하고 데모 대체 발생 여부를 검출하는 실패 테스트를 먼저 작성한다.

중단 조건:

- 기존 성공 작업의 응답 스키마가 깨지는 경우
- 사용자 응답에 로컬 경로나 비밀값이 포함되는 경우

롤백:

- 스키마는 추가 필드만 사용하고 기존 v1 큐 행을 계속 읽을 수 있게 한다.

### Phase 1 — 잘못된 성공 차단

변경 후보:

- `contracts/worker-job.schema.json`
- 신규 `contracts/final-export-job.schema.json`
- `01_app/render_server.py`
- `01_app/staged_ffmpeg_renderer.py`
- `01_app/auth_store.py`

작업:

1. 큐 등록 시 확정 리비전과 렌더·브랜드·선택 미디어 스냅샷을 만든다.
2. 스냅샷 전체에 `input_hash`를 생성한다.
3. 운영 렌더의 데모 영상·데모 나레이션 fallback을 제거한다.
4. 모든 장면의 `media_type`과 선택 자산이 일치하는지 검증한다.
5. 음성은 `cue_id + profile_id + text_hash + checksum`으로 검증한다.
6. 워커는 스냅샷 자산의 체크섬과 파일 존재를 확인한 뒤에만 자막·FFmpeg를 시작한다.

중단 조건:

- 정상 기존 프로젝트가 마이그레이션 없이 모두 렌더 불가가 되는 경우
- 미리보기에서 선택된 자산과 스냅샷이 다르게 해석되는 경우

롤백:

- v2 작업 생성만 feature flag로 끌 수 있게 하되 운영 데모 fallback 제거는 유지한다.
- 기존 큐 행은 v1 호환 실행기로 처리하고 신규 행만 v2 검증을 적용한다.

### Phase 2 — 비동기 요청과 멱등성

변경 후보:

- `01_app/render_server.py`
- `01_app/assets/steps/step04/step04-render-controller.js`
- `01_app/final_export_queue.py`
- `01_app/web_gateway.py`

작업:

1. `POST /render`는 등록 완료 후 즉시 `202 {job_id,status}`를 반환한다.
2. 음성 준비를 큐의 `voice_preflight` 단계로 옮긴다.
3. UI는 동일 `job_id`를 저장하고 상태 API만 폴링한다.
4. 세션 복원 후에만 렌더 설정과 상태를 조회한다.
5. `user_id + project_id + revision_id + input_hash`의 활성 작업은 하나만 허용한다.
6. 일시적 401·502·네트워크 오류에는 제한된 백오프를 적용하고 모든 종료 상태를 처리한다.

회귀 위험:

- 기존 UI가 200 응답에 바로 `exports`가 있다고 가정한다.
- 자동화 워커의 `/render` 호출 계약도 함께 바꿔야 한다.

롤백:

- API가 `Prefer: respond-async` 또는 버전 경로로 v1/v2를 잠시 병행한다.

### Phase 3 — 재시도, 제한시간, 취소

변경 후보:

- `01_app/final_export_worker.py`
- `01_app/final_export_queue.py`
- `01_app/staged_ffmpeg_renderer.py`
- `01_app/render_server.py`
- `docker-compose.yml`

작업:

1. 검증 오류, 영구 파일 누락, 지원하지 않는 형식은 재시도하지 않는다.
2. 일시적 SQLite 잠금, 프로세스 자원 부족, 명시적으로 분류된 I/O 오류만 제한 재시도한다.
3. FFmpeg 단계별 제한시간과 전체 작업 deadline을 둔다.
4. timeout·cancel 시 `terminate → 유예 → kill` 순서로 자식 프로세스를 정리한다.
5. 취소 API와 UI를 추가하고 장면·비율·오디오 단계 사이에서 취소를 확인한다.
6. 등록 단계 진입 뒤에는 취소를 거부하거나 보상 트랜잭션을 사용한다.
7. 큐에는 `cancel_requested_at`을 추가하고, 워커가 자식 프로세스와 임시파일 정리를 마친 뒤에만 상태를 `cancelled`로 확정한다.
8. 워커 SIGTERM 시 신규 작업 수신을 멈추고 현재 자식 프로세스를 유예 종료하며 컨테이너에는 `stop_grace_period`를 둔다.

회귀 위험:

- 너무 짧은 timeout은 정상 장시간 렌더를 오탐한다.
- 재시도 가능 오류를 넓게 잡으면 같은 비싼 작업을 반복한다.

롤백:

- timeout과 재시도 정책을 환경설정으로 조정하되 무제한 값은 허용하지 않는다.
- 초기 timeout은 영상 예상 길이에 비례한 넉넉한 값과 절대 상한을 함께 사용한다. 정상 작업의 timeout 오탐이 기준을 넘으면 상한을 우선 조정한다.

마이그레이션:

- `final_export_jobs.cancel_requested_at` 추가는 nullable 컬럼 추가로 처리한다.
- 기존 상태 CHECK 제약을 즉시 재작성하지 않고, 실제 종료가 끝났을 때만 기존 `cancelled` 상태를 사용한다.

## 6. 필수 검증 매트릭스

### 입력 불변성

- 큐 등록 뒤 대본을 수정해도 작업은 고정 리비전을 렌더한다.
- 큐 등록 뒤 브랜드·크롭·플랫폼 설정을 수정해도 진행 중 작업은 바뀌지 않는다.
- 입력 해시가 다르면 기존 MP4를 재사용하지 않는다.

### 미디어 완전성

- 이미지 장면의 선택 이미지가 없으면 큐 등록 또는 preflight가 실패한다.
- 영상 장면의 선택 Kling MP4가 없으면 명시적으로 실패한다.
- 음성 누락, text hash 불일치, 프로필 불일치를 각각 검출한다.
- 어떤 실패에서도 데모 영상·데모 음성이 최종본에 들어가지 않는다.

### 비율 및 브랜드

- 16:9, 1:1, 9:16, 4:5 각각 올바른 아웃트로 variant와 워터마크 설정을 사용한다.
- 한 비율 실패 시 어떤 비율도 캘린더에 부분 등록되지 않는다.
- 재시도 후 모든 비율의 `input_hash`가 같다.

### 복구와 동시성

- 브라우저를 닫고 다시 열어 같은 `job_id`로 진행률과 결과를 복구한다.
- 동일 버튼 연속 클릭과 두 탭 실행이 작업 하나로 수렴한다.
- 워커 SIGTERM, SIGKILL, 임대 만료, SQLite 잠금에서 중복 등록되지 않는다.
- 취소 후 FFmpeg 자식 프로세스와 임시파일이 남지 않는다.

### 캘린더와 보안

- 플랫폼별 같은 날짜 항목이 하나만 존재한다.
- 이전 최종본은 immutable version으로 유지된다.
- 다른 사용자와 비로그인 사용자는 artifact를 내려받지 못한다.
- 오류 응답과 상태 응답에 API 키, 로컬 경로, traceback이 없다.

### 전체 회귀

```bash

python3 -m unittest discover tests && \
PYTHONPATH=.:01_app python3 tests/test_random_api_e2e.py && \
```

실제 미디어 E2E에서는 출력별 FFprobe로 길이, 해상도, 30fps, H.264, AAC, yuv420p, faststart를 확인하고 최종 길이가 데이터 기반 타임라인과 일치해야 한다.

## 7. 구현 분할안

충돌을 피하기 위해 동시에 수정하지 않고 아래 경계로 나눈다.

코드 크기 원칙:

- 신규·수정 파일은 200줄 이내를 기본 한도로 한다.
- 200줄을 넘기기 시작하면 화면, 도메인 서비스, 저장소, 외부 프로세스 어댑터, API 계약 중 책임에 맞춰 별도 모듈이나 API로 분리한다.
- 주석 축소, 긴 한 줄, 기계적 파일 쪼개기로 줄 수만 맞추지 않는다. 공개 인터페이스가 작고 단방향 의존성을 가져야 한다.
- 기존 대형 파일은 이번 변경 범위를 더 키우지 않고, 수정하는 기능을 우선 추출한 뒤 원래 진입점에는 호환용 위임만 남긴다.
- 예외는 스키마·상수·생성 코드처럼 분리가 오히려 계약을 흐리는 경우로 제한하고, 계획 문서와 코드 리뷰에 이유를 기록한다.

1. 계약·큐 담당: 스냅샷 스키마, 입력 해시, 멱등성, 상태 전이
2. 렌더 담당: preflight, 데모 fallback 제거, 음성/cue 검증, timeout·cancel
3. 등록 담당: 원자적 artifact·brand·calendar finalize와 마이그레이션
4. 프런트 담당: 202 응답, 상태 복구, 세션 순서, 취소 UI
5. 최종 통합 담당: 계약 테스트, 전체 회귀, 실제 미디어 E2E, 배포·롤백 판단

같은 파일을 여러 담당자가 동시에 수정하지 않는다. `render_server.py` 변경은 계약 담당 결과가 확정된 뒤 순차 통합한다.

## 8. 권장 배포 순서와 게이트

각 묶음은 별도 커밋·배포 단위로 만들고, 다음 묶음은 직전 묶음의 회귀 및 실제 미디어 E2E 통과 뒤 시작한다.

1. 관측성: 안전한 오류 코드·단계·attempt와 서버 전용 traceback
2. 입력 신뢰성: v2 불변 스냅샷, 전체 preflight, 데모 영상·음성 대체 제거
3. 요청 복구성: `202 + job_id`, 브라우저 재접속 복구, 멱등키, TTS 큐 단계화
4. 확정 일관성: 모든 비율 검증 후 artifact·brand·calendar 원자 반영
5. 실행 제어: 재시도 분류, FFmpeg timeout, 취소와 SIGTERM drain
6. 보안·운영: 소유권 다운로드, 로컬 폰트, 임시파일 회수, 큐 공정성과 SQLite 쓰기 제한

세부 배포는 `오류 관측성 → 스냅샷+전체 preflight → 데모 대체 제거`를 P0의 세 단위로 나눈다. P1에서는 `원자적 finalize → 202 비동기 전환 → 취소·timeout` 순서가 안전하다. 인증 다운로드는 다른 계약과 독립 배포하되 외부 소비 경로를 먼저 확인한다.

배포 게이트:

- 스냅샷·큐 계약 변경 전 활성 큐를 비우거나 명시적으로 v1/v2 워커를 분리한다.
- `큐 등록 → 새 리비전 생성 → 원래 미디어·음성 제거` 시나리오는 데모 대체 없이 명시적으로 실패해야 한다.
- 위 실패 시나리오와 정상 시나리오를 16:9, 1:1, 9:16, 4:5 모두에서 확인한다.
- DB 마이그레이션 전 SQLite 파일과 데이터 볼륨 백업, Git 롤백 기준점을 만든다.
- 신규 스키마는 먼저 읽기 호환 코드를 배포한 뒤 쓰기를 전환하고, 구버전 큐 행이 소진된 후 호환 코드를 제거한다.

## 9. 완료 기준

- 잘못된 자산을 데모로 대체하는 성공 경로가 없다.
- 큐 행 하나가 하나의 불변 입력 해시와 연결된다.
- 일반 사용자 동작에서 중복 작업이 생성되지 않는다.
- 모든 비율과 캘린더가 전부 성공하거나 전부 미반영된다.
- 재시도·취소·timeout 뒤 고아 프로세스와 신규 고아 파일이 없다.
- 최종 MP4는 인증된 소유자만 접근한다.
- 전체 테스트와 실제 미디어 E2E가 모두 통과한다.
- 배포 전 SQLite와 데이터 볼륨 백업 및 Git 기준점이 준비된다.
